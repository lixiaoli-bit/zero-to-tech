HTTP · API · 手搓笔记 从调用方到服务方

API 与 HTTP

上一节我们安装了 Python，这一节我们用 Python 手搓一个 API。

核心关系： API 是程序对外提供能力的入口，而 HTTP 是这套入口上的对话协议。浏览器加载网页、curl 调接口，走的都是 HTTP。

HTTP 一去一回：请求和响应

请求（去） 响应（回） ├─ 请求行 ├─ 状态行 ├─ 请求头（若干行） ├─ 响应头（若干行） ├─ （一个空行） ├─ （一个空行） └─ 请求体 └─ 响应体
  • 请求：请求行 + 头 + 空行 + 体
  • 响应：状态行 + 头 + 空行 + 体
  • 全是纯文本，格式对称

curl -v 验证报文

curl -v 能把请求原文、响应原文全亮出来。

curl -v 'https://api.ipify.org?format=json' win不可以
curl -v https://ifconfig.me win可以
  • * 开头：curl 旁白
  • > 开头：发出去的请求原文
  • < 开头：收到的响应原文
理论一一对应： 请求行、头、空行、体 — 逐行可指认。

常见方法 · 常见头

GET “把某样东西给我”
POST “我提交一段内容，请你处理”
PUT 整个换掉
PATCH 改一部分
DELETE 删除
HEAD 只要头不要体

请求头 Request

Host 我要找哪台服务器
User-Agent 我是谁（工具 / 浏览器）
Accept 我能接受什么格式
Accept-Language 我偏好什么语言
Content-Type 我提交的请求体是什么格式
Content-Length 请求体有多长
Authorization 身份凭证（Bearer sk-…）
Cookie 随身带的“小纸条”

响应头 Response

Content-Type 我回的体是什么格式 （本节主角）
Content-Length 我回的体有多长
Server 我是什么服务器软件
Date 什么时间处理的
Cache-Control 缓存策略（能存多久）
Set-Cookie 发一张“小纸条”，下次记得带上
Location 内容搬家了，去这个新地址找（配合 3xx）
Access-Control-Allow-Origin 允许哪些来源的网页调用我
请求头是调用方的自我交代 响应头是服务方对内容的交代 日常开发了解这些足够，陌生头查再用

手搓 API · 用 Python 实现规范

新建 ~/zero-to-tech/backend/main.py

手搓 API 要处理 HTTP 的每一块。好在 Python 自带 http.server，接下来我们就用它逐项实现。

from http.server import BaseHTTPRequestHandler, HTTPServer import json profile = { "heroTitle": "关于我", "heroSubtitle": "项目，创意，灵感，心得，我的作品", } class Handler(BaseHTTPRequestHandler): def do_GET(self): if self.path == "/api/profile": self.send_response(200) self.send_header("Content-Type", "application/json") self.end_headers() body = json.dumps(profile, ensure_ascii=False) self.wfile.write(body.encode("utf-8")) else: self.send_response(404) self.end_headers() HTTPServer(("", 8000), Handler).serve_forever()
代码 ↔ 规范对照：
do_GET → 请求行里的方法
self.path → 请求行里的路径
self.send_response(200) → 状态行
self.send_header(...) → 响应头
self.end_headers() → 空行（分界线）
self.wfile.write(...) → 响应体

跑起来

python3 main.py 执行完命令光标不动不是卡死，而是serve_forever一直在守着8000端口

新终端窗口调用：

curl http://localhost:8000/api/profile

浏览器打开 http://localhost:8000/api/profile 也能看到 JSON。

动手实验 · 理解头与元信息

实验一：Content-Type 的威力

临时加 /hello 路径，对比 text/html 和 text/plain：

elif self.path == "/hello": self.send_response(200) self.send_header("Content-Type", "text/html; charset=utf-8") # 改成 text/plain 试试 self.end_headers() self.wfile.write("<h1>你好，HTTP</h1>".encode("utf-8"))
  • text/html → 浏览器渲染大标题
  • text/plain → 原样显示标签源码

    • 浏览器打开 http://localhost:8000/hello 记住：改动之后重启服务

实验二：服务端能看到什么

在 do_GET 开头加两行：

print(self.headers) # 请求头 print(self.client_address) # 来源 IP + 端口
  • curl -v http://localhost:8000/api/profile 再调用一次
  • curl 的 User-Agent 是 curl/8.7.1 User-Agent 是“我是谁”的自我介绍：curl 报名字和版本，浏览器报一长串型号，服务端一眼就能分清请求来自浏览器还是程序
  • 浏览器的 User-Agent 是一长串型号
  • client_address 显示来源 IP（本机是 127.0.0.1）
边界感： 服务端天然能看到 UA、IP、语言偏好。每个请求都比自己以为的更“透明”。

杂活 vs 框架

  • 手搓：路由、状态行、响应头、空行、响应体…… 一个接口尚且如此，十个接口要出人命。
  • 框架（FastAPI）把这些杂活打包复用，缩成几行。
  • 但正因为亲手搓过，我们确切知道框架替我们干了什么。

下一节：FastAPI 登场。

这一节你应该带走什么

  • HTTP 报文格式：请求 ＝ 请求行＋头＋空行＋体；响应 ＝ 状态行＋头＋空行＋体
  • 方法描述意图（GET/POST），不是数据方向；curl 默认 GET，带 -d 变 POST
  • 状态码家族：2xx 成功，4xx 请求方问题，5xx 服务方问题
  • 硬要求：状态行、空行；实践必写：Content-Type
  • Content-Type 一变，对方处理方式就变（HTML vs JSON）
  • 我们的第一个 API：零依赖，纯标准库，serve_forever() 一直跑着等请求
  • curl -v / F12 随时能看报文原文
  • 任何语言写后端，都是在实现同一套 HTTP 规范 → 所以有了框架
